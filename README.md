## 一、项目目标

实现一款**跨平台、可脚本化、带 Web 图形界面**的数据备份与还原软件：

- **基础能力（法定必做，40 分）**
  - **数据备份**：将目录树中的文件完整保存到指定位置
  - **数据还原**：将备份内容原样恢复到指定位置
- **扩展能力（自选，上不封顶）** —— 分两档推进，详见 [§2](#二扩展功能选型与得分规划)
  - **必选档（P0）**：压缩解压 · 加密解密 · 自定义备份 · 元数据支持 · 图形界面
  - **备选档（P1）**：打包解包 · 定时备份 · 文件类型支持 · 实时备份 · 网络备份

设计上刻意追求三点，因为它们直接对应评分标准中「**重点考察正确性、易用性、健壮性**」：

| 评分关注点 | 本项目的应对方式 |
|---|---|
| **正确性** | 元数据清单带 CRC32 校验 + 可 `verify` 自检；还原后与原目录逐字节比对 |
| **易用性** | Web GUI（目录树浏览 + 表单式筛选规则 + 实时进度条），提供 CLI 供脚本调用 |
| **健壮性** | 中断可续、磁盘满/权限拒绝/超长路径/符号链接环 均有明确处理与错误上报 |

## 二、扩展功能选型与得分规划

评分规则中**每种算法 10 分是唯一可叠加计分的项**，因此本项目把工程重心放在这里：用插件式算法注册表，每多接入一种算法，边际成本约 30 行代码，却能再多拿 10 分。

### 2.1 必选扩展（P0 · 必须全绿）

| 扩展项 | 计分方式 | 本项目实现 | 小计 |
|---|---|---|---|
| **压缩解压** | 每种算法 10 分 | **DEFLATE**(zlib) + **LZ4** + **Zstandard** + **RLE**(自研) | **40** |
| **加密解密** | 每种算法 10 分 | **AES-256-CBC** + **ChaCha20-Poly1305** + **RC4**(自研) | **30** |
| **自定义备份** | 每项 3 分 | 路径 / 类型 / 名字 / 时间 / 尺寸 / 用户 **全 6 项** | **18** |
| **元数据支持** | 满分 10 分 | 权限位、属主属组、三类时间戳、属主名、Windows 文件属性、ACL | **10** |
| **图形界面** | 满分 10 分 | Web GUI（目录树 + 任务面板 + 进度 SSE + 算法选择） | **10** |
| | | **必选扩展分小计** | **108** |

> **保底口径**：若时间紧张，压缩只接 3 个库算法（−10）、加密只接 2 个库算法（−10），必选仍有 **88 分**。
> 自研的 RLE 与 RC4 代码量合计约 100 行，是整份清单里性价比最高的一次投入。

### 2.2 备选扩展（P1 · 必选完成后再上）

| 扩展项 | 计分方式 | 本项目实现 | 小计 |
|---|---|---|---|
| **打包解包** | 每种算法 10 分 | **VBAK 自研索引格式** + **USTAR 兼容格式** | **20** |
| **定时备份** | 满分 10 分 | Cron 风格周期调度 + **数据淘汰**（保留 N 份 / GFS 策略） | **10** |

| **网络备份** | 分项累加 | 网盘模式 10 + 用户管理 5 + 元数据管理 5 + 传输加密 5 + 增量备份 5 | **30** |
| | | **备选扩展分小计** | **85** |

### 2.4 关于「打包解包」被列为备选

这个划分**在架构上是成立的**，因为两个概念对应两种不同的输出模式：

| | 基础要求 | 打包解包 |
|---|---|---|
| 原文描述 | 将目录树中的文件保存到**指定位置** | 将所有备份文件**拼接为一个大文件** |
| 输出形态 | **目录镜像**（一棵树 + 一个 manifest） | **单容器**（一个 `.vbak` 文件） |
| 是否必须 | ✅ 法定必做 | 备选扩展 |

因此备份引擎设计为 **Repository 抽象 + 两种后端**：

```
                    ┌─► 目录镜像后端 ──► out/docs/...        + .backup-manifest.json
Repository (抽象) ──┤
                    └─► 单容器后端   ──► out/docs.vbak
```

两种后端**共用**筛选引擎、压缩/加密算法注册表、元数据定义与还原逻辑，差异只在"数据往哪儿写"。这意味着：

- **必选部分不会因打包解包延后而阻塞** —— M1 先做目录镜像模式即可跑通基础 40 分。
- **备选部分启动时边际成本很低** —— 打包解包本质上是"再加一个 Repository 后端"，而非从头造轮子。
- **元数据存储格式在两种模式下高度重合** —— 目录镜像模式的 manifest 与单容器的索引区结构一致，设计一次即可服务两边（见 §5）。

> **一个必须提前定的细节**：`元数据支持` 是必选，而元数据必须有载体。目录镜像模式下的载体就是 manifest 文件。所以**manifest 格式必须在 M1 就定下来**，不能等打包解包。好在这与 §5 的索引区设计是同一套结构。

### 2.5 关于「调库算不算实现」

主力算法（DEFLATE/LZ4/Zstd/AES/ChaCha20）调用成熟库保证**正确性与健壮性**，这是工程上的正确选择；同时**自行实现 RLE 压缩与 RC4 流加密**两个算法，代码完全自研，用来坐实「自研算法」这一栏。建议开学第一周就找老师口头确认该口径。

## 三、技术栈

### 3.1 后端（C++）

| 用途 | 选型 | 理由 |
|---|---|---|
| 语言 | **C++17** | 课程主线语言，扩展分考的就是工程实现能力 |
| 构建 | **CMake ≥ 3.20** | 跨平台，IDE 无关 |
| 依赖管理 | **vcpkg**（manifest 模式）<br>triplet = **`x64-windows-static`** | Windows 下装 zlib/zstd/openssl 最省事；静态 triplet 是单 exe 交付的前提，见 §3.4 |
| HTTP 服务 | **cpp-httplib** | 单头文件，无需理解 socket/线程池，十余行即可起服务 |
| JSON | **nlohmann/json** | 单头文件，前后端数据交换 |
| 压缩 | **zlib / lz4 / zstd** | 三种算法各计 10 分 |
| 加密 | **OpenSSL 3.x** | AES-256-CBC、ChaCha20-Poly1305 |
| 文件监控 | `ReadDirectoryChangesW`(Win) / `inotify`(Linux) | 实时备份（15 分，**备选**，排在备选末段） |
| 桌面外壳 | **webview**（可选，P2） | 单头文件，把 Web UI 包成原生窗口并暴露原生目录对话框 |
| 测试 | **Catch2** | 单头文件，写测试零负担 |

### 3.2 前端

**原生 HTML + CSS + JavaScript**，零框架、零构建步骤，由 C++ 后端直接托管静态文件。

- `fetch` 调用 REST API
- `EventSource` 订阅 SSE 实时推送备份进度与文件变化事件
- `desktop/` 桌面外壳（可选）下，额外通过 `typeof window.pickDir === 'function'` 探测原生能力

#### 两种可切换的外壳

前端代码**不含任何"外壳知识"**，只与 HTTP API 对话，因此交付形态可在最后阶段零成本切换：

| | ① 浏览器模式 | ② 桌面外壳模式（可选加分项） |
|---|---|---|
| 使用方式 | 运行 exe → 打开浏览器访问 `localhost:8080` | 双击 exe → 直接弹出独立窗口 |
| 开发体验 | F12 调试、改 CSS 刷新即见、可用 curl 单测后端 | 同左（底层仍是同一套服务） |
| 目录选择 | 服务端目录树 `/api/fs/list` | **原生对话框**（经 `webview` 的 `bind` 调 Win32 API），拿到真实绝对路径 |
| 代码增量 | — | 约 15 行，`desktop/main.cpp` |

```cpp
// desktop/main.cpp —— 全部内容
webview::webview w(false, nullptr);
w.set_title("文件备份软件");
w.set_size(1200, 800, WEBVIEW_HINT_NONE);
std::thread([]{ startHttpServer(); }).detach();   // 复用同一套 server
w.bind("pickDir", [](std::string) { return nativeFolderDialog(); });
w.navigate("http://127.0.0.1:8080");
w.run();
```

桌面外壳是**加分项而非必需项**：若 `webview` 集成受阻，直接退回浏览器模式交付，前端与后端零改动。这层设计的意义在于**把技术不确定性交给架构吸收，而不是提前赌一个方案**。

#### 目录选择的降级策略

浏览器安全模型禁止网页获取本地文件的真实绝对路径，因此前端按能力探测降级：

```js
async function pickDirectory() {
  if (typeof window.pickDir === 'function') return await window.pickDir(); // 桌面外壳：原生对话框
  return await showServerTreePicker();                                     // 浏览器：服务端目录树
}
```

### 3.3 为什么不是 Qt

Qt6 曾作为备选评估过，最终未采用。决策依据：

1. **界面人力**：组内界面负责人使用 HTML/CSS/JS 更熟练，Qt 需要现学信号槽与 Model/View 体系，用组员短板对线不划算。
2. **迭代速度**：Web 前端改样式刷新即见；Qt 每次调整布局都要重编译，配置类界面（本项目的筛选规则表单相当复杂）迭代成本高。
3. **实时/定时备份不构成 Qt 的理由**——这两项无论如何都应实现在 C++ 后端，前端只是订阅方。Qt 真正省下的仅是手写文件监控的约 120 行，不足以抵消上述两点。

**代价与对策**：放弃 Qt 后需自行实现两处，均已评估为可控——

| 失去的能力 | 替代方案 | 工作量 |
|---|---|---|
| `QFileSystemWatcher` | `ReadDirectoryChangesW`(Win) / `inotify`(Linux) | 约 120 行 |
| `QFileDialog` | 服务端目录树 API，或桌面外壳下的原生对话框 | 见 §3.2 |

### 3.4 交付形态：单 exe

**目标：最终产出为单个 `FileBackup.exe`，双击即用，无任何外部依赖。**

不选单 exe 本身不算错，但它会引入一类**课设演示最常见的翻车方式**：拷贝到演示机器上少一个 DLL，当场打不开。静态链接让这个问题在物理上不可能发生。

阻止单 exe 的四件事与对策：

| # | 障碍 | 对策 |
|---|---|---|
| ① | 依赖库 DLL（`zlib1.dll`、`lz4.dll`、`zstd.dll`、`libcrypto-3-x64.dll`…） | **vcpkg 用 `x64-windows-static` triplet**，库代码直接编入 exe |
| ② | MSVC 运行库 DLL（`msvcp140.dll`、`vcruntime140.dll`…） | 同上，配套设置静态 CRT（见下方警告） |
| ③ | `web/` 前端文件需在运行时从磁盘读取 | 构建期用 `tools/embed_web.py` 转成 C++ 字节数组编入 exe，HTTP 服务改为从内存响应 |
| ④ | `WebView2Loader.dll`（仅桌面外壳模式） | 可静态链接；归入 M7 技术验证项，**不在关键路径** |

> ⚠️ **必须在装 vcpkg 时就选定 triplet。** `x64-windows-static` 的库以 `/MT` 编译，若自身代码用默认的 `/MD`，链接会报 `LNK2038: RuntimeLibrary 不匹配`。对应地在 `CMakeLists.txt` 中设置：
> ```cmake
> set(CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>")
> ```
> **事后修改 triplet 需要重编全部依赖**（OpenSSL 一步约 10–20 分钟），因此这是一个"一次选对、永不返工"的决定。

**预期体积**：约 20 MB（静态链接 + 嵌入前端），桌面外壳版约 25 MB。主要来自 OpenSSL 的 `libcrypto`，属正常代价。

**关于 WebView2 Runtime**：Windows 11 已预装，无需随 exe 分发。若需支持 Windows 10，则要另行说明（本课程演示环境不涉及）。

**外壳可插拔**：`web/` 中的前端代码不含任何"外壳知识"，只与 HTTP API 对话。因此"浏览器访问"与"桌面窗口"两种交付形态可以在最后阶段零成本切换（见 §3.2）。

## 五、归档格式规范（VBAK v1）

这是整个项目的技术核心，也是系统设计文档的重点章节。

### 5.0 两种输出模式共用同一套结构

按 §2.4 的设计，`Entry Index` 这一节的结构**有两种落地形式**，内容完全一致：

| 模式 | 落地形式 | 说明 |
|---|---|---|
| **目录镜像**（必选） | `out/docs/.backup-manifest.json` | 一棵目录树 + 一个 manifest 文件；文件本身放在树中对应位置 |
| **单容器**（备选） | 单个 `docs.vbak` 文件 | manifest 作为「索引区」写在归档尾部 |

也就是说：**先定义好 Entry 与 MetaBlock 的结构，两种模式只是把它序列化到不同地方。** 这是把打包解包列为备选却不影响元数据支持（必选）的关键。

下方为**单容器模式**的完整布局；目录镜像模式下忽略 Header/Footer/Data Blocks，只保留 Entry Index 部分作为 manifest 内容。

```
┌──────────────────────────────────────────────────┐
│  File Header (64 B)                              │
│    magic        char[4]   "VBAK"                 │
│    version      uint16    1                      │
│    flags        uint16    bit0 索引在尾部         │
│                           bit1 全档已压缩         │
│                           bit2 全档已加密         │
│    pack_id      uint8     0=VBAK 1=USTAR         │
│    comp_id      uint8     0=none 1=deflate        │
│                           2=lz4 3=zstd 4=rle     │
│    enc_id       uint8     0=none 1=aes256cbc      │
│                           2=chacha20poly1305 3=rc4│
│    entry_count  uint64    条目数                  │
│    index_offset uint64    索引区起始偏移          │
│    index_length uint64    索引区长度              │
│    reserved     byte[24]  预留                    │
├──────────────────────────────────────────────────┤
│  Data Blocks                                     │
│    逐条目顺序写入的（压缩+加密后的）文件数据       │
├──────────────────────────────────────────────────┤
│  Entry Index                                     │
│    每条目：                                       │
│      path_len   uint16                            │
│      path       char[]    相对路径，UTF-8          │
│      type       uint8     0文件 1目录 2符号链接    │
│                           3硬链接 4FIFO 5设备      │
│                           6socket 7其他           │
│      orig_size  uint64    原始大小                 │
│      stor_size  uint64    存储大小                 │
│      crc32      uint32    原始内容 CRC32          │
│      data_off   uint64    数据块偏移               │
│      link_target char[]   链接目标（type≥2 时）    │
│      meta       MetaBlock 见下                    │
│      iv         byte[16]  加密算法 IV（enc≠0 时）  │
├──────────────────────────────────────────────────┤
│  Footer (32 B)                                   │
│    index_crc32  uint32                            │
│    archive_crc32 uint32                           │
│    magic        char[8]   "VBAKEND"              │
└──────────────────────────────────────────────────┘
```

**MetaBlock 内容**（对应「元数据支持」10 分）：

| 字段 | 平台 | 说明 |
|---|---|---|
| `mode` | 全平台 | 权限位（RWX） |
| `uid` / `gid` | Linux | 属主 / 属组 ID |
| `owner` / `group` | 全平台 | 属主 / 属组名（跨机还原用） |
| `mtime` / `atime` / `ctime` | 全平台 | 修改 / 访问 / 创建时间（纳秒精度） |
| `win_attrs` | Windows | 只读/隐藏/系统/存档 属性位 |
| `acl` | Windows | 安全描述符（`GetFileSecurity` 导出） |

### 5.1 关键设计决策

1. **索引置于尾部** —— 支持流式写入，无需预先知道文件数量；同时为「快速列出归档内容」和「单文件还原」提供 O(log n) 定位，不必解压整个归档。
2. **管线顺序 = 打包 → 压缩 → 加密** —— 先压缩后加密是密码学常识：加密后的数据是高熵的，无法再被压缩。这个顺序本身就是一个值得写进设计文档的论证点。
3. **逐条目独立压缩/加密** —— 每条目自带 IV 与偏移，代价是略微损失跨文件压缩率，换来的是**单文件还原无需解密全档**，恢复大归档中的一个小文件从分钟级降到毫秒级。
4. **CRC32 双重校验** —— 索引区与全档各一个校验值，配合逐条目的 `crc32`，可精确定位损坏位置而非笼统报「文件损坏」。

## 六、算法模块清单

所有算法通过注册表模式接入，统一接口：

```cpp
class IPacker     { virtual void pack(...);   virtual void unpack(...);   };
class ICompressor { virtual void compress(...); virtual void decompress(...); };
class ICipher     { virtual void encrypt(...); virtual void decrypt(...); };
```

新增一个算法 = 实现接口 + 在注册表注册一行 + 前端下拉框自动出现（`/api/algorithms` 动态返回）。

### 打包解包（20 分）· 备选

| ID | 名称 | 类型 | 说明 |
|---|---|---|---|
| `vbak` | VBAK 索引格式 | 自研 | 带尾部索引，支持随机访问单文件 |
| `ustar` | USTAR 兼容格式 | 标准 | 生成的归档可用系统 `tar` 解开，是格式正确性的有力证明 |

> 属于 §2.2 备选扩展。作为第三个 Repository 后端接入，与目录镜像后端共用筛选、算法与元数据逻辑。

### 压缩解压（40 分）· 必选

| ID | 名称 | 依赖 | 特点 |
|---|---|---|---|
| `deflate` | DEFLATE | zlib | 通用，压缩率高 |
| `lz4` | LZ4 | lz4 | 极快，适合实时备份场景 |
| `zstd` | Zstandard | zstd | 现代算法，压缩级别可调（1–19） |
| `rle` | 游程编码 | **自研** | 教学经典算法，约 60 行，坐实自研分 |

### 加密解密（30 分）· 必选

| ID | 名称 | 依赖 | 特点 |
|---|---|---|---|
| `aes256cbc` | AES-256-CBC | OpenSSL | 工业标准；密钥由用户密码经 **PBKDF2-SHA256**（10 万次迭代 + 随机盐）派生 |
| `chacha20poly1305` | ChaCha20-Poly1305 | OpenSSL | AEAD，加密同时保证完整性，能检测篡改 |
| `rc4` | RC4 流加密 | **自研** | 流密码经典算法，约 40 行 |

> 安全提示：RC4 在密码学上已被认为不安全，本项目仅作教学演示用途，**生产环境默认使用 AES-256-CBC 或 ChaCha20-Poly1305**。

### 筛选规则（18 分）· 必选

六个维度全部实现，规则以 JSON 数组下发，支持 AND/OR 组合与 include/exclude：

| 维度 | 配置形式 | 示例 |
|---|---|---|
| 路径 | glob 前缀匹配 | `/home/*/docs/**` |
| 类型 | 扩展名 / 分类 | `*.jpg,*.png` 或 `category:image` |
| 名字 | 文件名 glob | `report_*.pdf` |
| 时间 | mtime 区间 | `last 7 days` / `2025-01-01..2025-06-30` |
| 尺寸 | 区间 | `< 100MB`、`1KB..10MB` |
| 用户 | 属主 | `uid:1000` 或 `owner:alice` |

## 七、接口设计

### 7.1 CLI（供脚本调用 / 自动化测试）

```bash
# 备份
FileBackup backup --src ./docs --dst ./bak/docs.vbak \
                  --pack vbak --compress zstd --level 15 \
                  --encrypt aes256cbc --password ****** \
                  --filter '{"size":{"max":"100MB"}}'

# 还原（可只还原单个文件）
FileBackup restore --archive ./bak/docs.vbak --dst ./restored
FileBackup restore --archive ./bak/docs.vbak --dst ./out --entry "sub/a.txt"

# 查看归档内容 / 校验完整性
FileBackup list   --archive ./bak/docs.vbak
FileBackup verify --archive ./bak/docs.vbak
```

### 7.2 REST API（供 Web GUI）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/status` | 服务健康状态 |
| `GET` | `/api/algorithms` | 返回可用打包/压缩/加密算法列表（前端下拉框动态生成） |
| `GET` | `/api/fs/list?path=` | **服务端目录浏览**，供前端路径选择器使用 |
| `POST` | `/api/backup` | 创建备份任务 |
| `POST` | `/api/restore` | 创建还原任务 |
| `GET` | `/api/tasks` | 任务列表 |
| `GET` | `/api/tasks/{id}/stream` | **SSE** 推送任务实时进度 |
| `GET` | `/api/archives` | 归档文件列表 |
| `GET` | `/api/schedule` | 定时任务配置读写 |
| `GET` | `/api/watch/stream` | **SSE** 推送实时监控事件流 |

> **路径选择器的由来**：浏览器安全模型禁止网页获取本地文件的真实绝对路径（`<input webkitdirectory>` 只给相对路径）。因此前端不能直接用系统目录选择对话框，改为实现 `/api/fs/list`，由后端枚举服务端文件系统并在网页中渲染一棵可点击的目录树。这既绕开了限制，又能做得比原生对话框更直观（可同时展示文件大小、修改时间，并支持按筛选规则预览命中文件数）。
>
> 在桌面外壳模式（§3.2）下，`window.pickDir` 可用，前端将优先走原生对话框拿真实路径，本接口自动降级为备用。

### 7.3 前端接口约定

前端对后端的所有调用都封装在 `web/api.js` 一个文件里，`app.js` 只依赖该模块的语义化方法，不直接出现 URL 字符串。这样即使日后把 HTTP 换成 `webview` 的 `bind` 直调，也只改 `api.js` 一个文件。
